Hash tables and collisions

How does a dictionary find your key without searching?

You write users["dana"] and the value comes back at once. Ten keys or ten million, the wait is about the same. This page shows the mechanism with numbers small enough to check by hand.

setup

What a plain list has to do

Start with the familiar case. A list keeps keys in arrival order. To find one, you compare from the top.

The cost grows with the list. Sorting helps: binary search needs about 20 comparisons for a million keys. A hash table aims for one or two at any size.

mechanism 1

Turn the key into a position

A hash table is an array of buckets plus one rule. The rule is a hash function: it turns any key into a number. That number modulo the bucket count is the bucket index. The hash used here is about the simplest one possible: add up the character codes.

The function is deterministic. Insert and lookup run the same arithmetic and arrive at the same bucket. The work depends on the length of the key. The number of stored keys never enters the calculation.

mechanism 2

Two keys, one bucket

There are more possible keys than buckets, so some keys must share an index. That is a collision, and every hash table needs a policy for it. The classic policy is separate chaining: each bucket holds a linked list of the keys that landed there.

A lookup hashes the key, opens one bucket and compares along that chain only. Its cost is the length of one chain. The load factor is keys divided by buckets, which is also the average chain length. It is the number to watch.

mechanism 3

Growing the table

When the load factor passes a threshold, the table allocates a bigger array and places every key again. Java's HashMap does this above 0.75 and doubles the array. Each index depended on the old bucket count, so each key is reduced again with the new one.

Doubling has a tidy property. A key in bucket i of 4 can only land in bucket i or i + 4 of 8, so each chain splits into at most two. A resize touches every key, but it happens rarely enough that the average cost of an insert stays constant.

The last frame shows what resizing cannot fix. cat and act are anagrams, and a sum ignores letter order, so they collide at every size. Production hash functions mix each character with its position, which pulls similar keys apart. Many are also seeded per process so that nobody can prepare a set of colliding keys in advance.

contrast

The other design: open addressing

Chaining stores collided keys outside the array. Open addressing keeps everything inside it: one key per slot, and on a collision the insert tries other slots in a fixed order. The simplest order is linear probing, which tries the next slot down.

Probing is kind to CPU caches because neighbours sit in adjacent memory. The price is clustering, so these tables stay well below full. CPython's dict uses open addressing and grows once it is two-thirds full. Deletes need care: emptying a slot would cut the path to keys stored past it, so implementations leave a tombstone marker in its place.

payoff

The key's own characters say which bucket to open.

  • A lookup is one hash, one bucket and a short walk.
  • Load factor is keys divided by buckets. Keep it near 0.75 or lower and the walks stay short.
  • A resize rehashes every key. A weak hash function still collides afterwards.
