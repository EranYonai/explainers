why a flaky test lies

Why did the same test pass, then fail, with no code change?

You have seen it. Green yesterday, red this morning, green again on rerun. No commit landed in between. A test is supposed to report on your code, so something else must be deciding the result.

One test, one hidden guess

This test saves an order on a worker thread, waits 50 ms, then checks the result.

def test_save_marks_order():
    order = Order()
    pool.submit(save, order)  # worker
    time.sleep(0.050)         # "enough"
    assert order.saved

The save usually takes about 40 ms. Someone measured it once, added a margin and moved on. The test now carries a guess: the worker will finish before the sleep does. Nothing in the code enforces that order. Step through two runs of the same commit.

scene 1 · two runs, same code

Both runs executed identical code. The only difference was when the operating system let each thread run. That ordering is the interleaving, and here it decides the verdict. This is a race condition: two threads touch order.saved, and nothing forces the write to come before the read. In run 2 the product code was correct. The test asked too early.

Why it fails only sometimes

The pause in run 2 came from the machine: another process, a garbage collection, a noisy neighbour on a shared CI runner. Every run draws a different delay. Three things show up. The failure rate depends on the machine, which is why the test is green on a laptop and red on a loaded runner. A longer sleep thins the tail and never removes it, while every run pays for the extra wait. Waiting for the worker removes the race, and the test gets faster.

the answerThe code never changed. The timing did, and the test was measuring the timing.

Other common causes

A race is one cause. The others share its shape: the outcome depends on something the test does not control.

  • Shared state. One test leaves a row, a file or a global behind, and another test reads it.
  • Order dependence. A test passes only when a particular test ran before it. Shuffle or parallelise the suite and it breaks.
  • Time and timezones. Code that reads the real clock fails near midnight, at month end, across a daylight-saving change, or on a runner set to UTC.
  • Network. A call to a real service inherits that service's latency, rate limits and outages.

Why retries hide the bug

Say the test fails 5% of the time and CI retries it twice. The pipeline goes red only when all three attempts fail: 0.05 × 0.05 × 0.05, about 1 run in 8,000. The dashboard turns green. The race is still there.

Two costs follow. If the race lives in product code, users meet it too, and production has no rerun button. And the team learns that red means "run it again", so the next real regression gets rerun as well. The green lies in the same way: a passing run proves that one interleaving worked.

What to do

  • Make timing deterministic. Wait on the event itself: join the thread, await the future, or poll for the condition with a generous timeout. Replace real sleeps and real clocks with a fake clock the test controls.
  • Quarantine with an owner. Move the flaky test out of the blocking gate so it stops costing everyone time. Give it a named owner and a deadline. A quarantine nobody owns is a slow deletion.
  • Track flake rate per test. Count every pass-after-retry as a flake. The per-test rate tells you what to fix first and whether a fix worked. For a test that flaked 2% of the time, it takes about 150 green runs in a row to be 95% sure the flake is gone.
The simulation models extra delay as an exponential distribution whose mean is the jitter setting. Real schedulers are messier; the shape of the lesson is the same.
