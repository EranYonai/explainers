How does an explainer get made in one evening, with no camera and no voice?

This page was planned in one evening by one engineer and an AI, mostly from a phone. It answers two questions. For engineers: how does git find the one commit that broke the build? For creators: what process turns that answer into a lesson? The process has seven steps.

  1. InterviewAI asks
  2. Beatsyou approve
  3. Storyboardyou react
  4. GenerateAI writes
  5. Self-checkAI checks
  6. Iterateyou steer
  7. Publishyou ship

The engine described here does not exist yet. An AI wrote this page as plain HTML to test the idea. The dialogue below is reconstructed to show the process, and a real session is longer and messier.

Before anything is drawn, the AI asks questions. The answers become a brief of four lines. A weak brief gives a pretty animation that teaches nothing, so this step comes first.

Beats, then a storyboard you approve

The brief turns into four beats: hook, intuition, mechanism, payoff. You approve the outline in words. Then each beat gets one rough still. Stills are cheap to throw away, so this is the moment to object.

States, not animations AI writes

Now the AI writes the scene. The file lists objects and numbered steps. Each step says what is true: c4 is good, the suspects are c5 to c8. It never says how things move. The engine would own timing and easing, because an AI is reliable with facts and unreliable with motion curves. Step through and watch which lines are active.

After the self-check you steer in plain words, such as "slow down step 3", or you edit the file yourself. Then you publish. Here is the result.

One commit in 1,000 broke the build. How does git find it in ten tests?

Start small. Your nightly build was green at c1 and is red at c8. One of the seven commits after c1 introduced the bug.

git bisect tests the commit in the middle of the suspects. If the middle passes, the bug came later and everything up to that commit is cleared. If it fails, the bug is there or earlier. Either way, one test removes about half of the suspects.

Choose where the bug hides, then step through. These steps are generated by running the search, so they cannot disagree with the algorithm.

Now scale it up. Doubling the history adds one test.

One by one
Bisect

Every test halves what is left. 1,000 commits, 10 tests.

That is log2(n): the number of times you can halve n suspects before one remains.

Bisect rests on one assumption: once the bug appears, every later commit has it. A flaky test breaks that assumption and sends the search to the wrong commit. If a commit cannot be built, git bisect skip moves to a neighbour. Given a script that exits 0 on a pass, git bisect run ./test.sh does the whole search unattended.
