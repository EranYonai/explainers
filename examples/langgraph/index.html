Why did LLM apps move from chains to graphs?

Early LLM apps were built as pipelines. Today's agents are built as graphs with loops in them. Something forced that change. Ride five short lines to find out what.

1 Red line

One call, then a chain

A language model call is one stop. Text goes in, text comes out, and the model remembers nothing afterwards.

Real apps need more around that call. You fill a prompt template, call the model, then parse the reply into something your code can use. LangChain made that a chain: steps joined with the pipe operator, each output feeding the next input.

    2 Planned works

    Where the straight line breaks

    A chain fixes its route before the train leaves. That works for summarise-this or translate-that. It stops working once the next step depends on what just happened.

    Agents made this unavoidable. An agent lets the model decide whether to call a tool, reads the result, and decides again. Nobody knows in advance how many laps that takes.

    3 Teal loop

    LangGraph: state rides the network

    LangGraph replaces the pipeline with a map. Three ideas carry it.

    State is the train. It is one shared object, here a list of messages, that visits every station. Nodes are stations: plain functions that read the state and return only the keys they change. A reducer decides how that update merges in. For messages, the add_messages reducer appends. With no reducer, the new value replaces the old one.

    Edges are track. A normal edge always goes to the same next station. A conditional edge is a junction: a routing function reads the state and returns the name of the next node. Point an edge backwards and you have a cycle.

    Below is the standard agent loop. You play the model. Each time the train reaches it, decide whether it asks for a tool.

      That whole map is a few lines of Python. The loop is the last add_edge: tools always return to the model.

      from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import InMemorySaver

class State(TypedDict):
    messages: Annotated[list, add_messages]  # reducer: append

def call_model(state: State):
    # model = a chat model with tools bound
    return {"messages": [model.invoke(state["messages"])]}

def run_tools(state: State):
    ...  # run each requested tool, return ToolMessages

def route(state: State):
    last = state["messages"][-1]
    return "tools" if last.tool_calls else END

builder = StateGraph(State)
builder.add_node("model", call_model)
builder.add_node("tools", run_tools)
builder.add_edge(START, "model")
builder.add_conditional_edges(
    "model", route, {"tools": "tools", END: END})
builder.add_edge("tools", "model")           # the cycle

graph = builder.compile(checkpointer=InMemorySaver())
      4 Violet line

      Checkpoints and a red signal

      Because the state is one explicit object, it can be saved. Compile the graph with a checkpointer and LangGraph persists the state as checkpoints under a thread_id. The same thread can continue a conversation later.

      Saved state also lets a run stop for a person. A node calls interrupt(), the graph pauses, and the value you passed is handed to the caller. To continue, invoke the graph again on the same thread with Command(resume=...). Here the agent wants to send an email. You hold the signal.

      The answer

      Chains to graphs · single journey

      A chain can only go forward. Agents have to loop, branch, wait and resume, so the route became a graph and the cargo became shared state.

      Validated

      Chains did not disappear. A fixed pipeline is still the right shape for a fixed job. The graph is what you reach for when the model, a tool result or a person decides the next stop.
